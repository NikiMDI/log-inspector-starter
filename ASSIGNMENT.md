# Задание на допуск: «Кто положил сервис?»

## Что нужно сделать

Разработайте **на Go** сервис фонового анализа access-логов Nginx.
Пользователь загружает файл, получает номер задания, проверяет статус и забирает JSON-отчёт.
Фронтенд не требуется. Проект выполняется в течение семестра и демонстрируется на ноутбуке студента.

В комплекте даны только минимальный Go-каркас, генератор логов и контрольные файлы
с ожидаемым отчётом. Анализатор, работу с БД и инфраструктуру реализует студент.
Go-приложение в комплекте — только проверка запуска `/health`, не готовый анализатор.

## 1. Вход и отчёт

Вход — JSON Lines: одна запись запроса на строку. Обязательные поля:
`time` (RFC 3339), `ip` (IP-адрес), `method` (непустая строка),
`path` (путь без query-параметров), `status` (100–599),
`request_time` (неотрицательное конечное число секунд).
Пустую строку можно пропускать. Некорректная запись завершает анализ ошибкой с номером строки.

Отчёт содержит:

- общее количество запросов;
- число ответов 500–599 и их долю в процентах;
- топ-10 маршрутов по числу запросов;
- топ-10 маршрутов по средней длительности;
- топ-10 IP по числу запросов;
- число запросов и ответов 5xx по минутам UTC.

Маршрут — пара «метод + точный путь». Шаблоны адресов восстанавливать не нужно.
Время округляется вниз до начала минуты. Порядок записей во входе произвольный.
Показывайте только минуты, присутствующие во входе, по возрастанию.
Топы сортируются по убыванию показателя, при равенстве — по методу и пути
или IP лексикографически. Для пустого файла: нулевые счётчики и пустые списки.
Формат ответа показан в `fixtures/expected.json`. Допустимая погрешность дробных чисел — 0.000001.

## 2. API и фоновые задания

- `POST /jobs` — файл в теле запроса (`application/x-ndjson`), ответ 202 с `id`.
- `GET /jobs/{id}` — состояние и текст ошибки, если она возникла.
- `GET /jobs/{id}/report` — готовый отчёт; до готовности — 409.
- `GET /health` — проверка, что HTTP-приложение работает.

Неизвестный идентификатор — 404. Ограничение размера загрузки — 413.
Формат остальных ошибок выбирается самостоятельно и описывается в README.

Состояния: `queued`, `running`, `done`, `failed`.
После загрузки и регистрации файла HTTP-запрос заканчивается: анализ выполняется в фоне.
Задания выполняет фиксированное число worker, задаваемое настройкой.
Для основной версии можно периодически читать ожидающие задания из БД:
не нужно создавать отдельный брокер, распределённую очередь или собственный фреймворк.
Каждое задание внутри одного процесса должно выполняться одним worker.

## 3. Память и ошибки

Читайте файл последовательно. Нельзя хранить в памяти все исходные записи.
Агрегаты по маршрутам, IP и минутам можно хранить в map.
Предусмотрите настраиваемый предел размера файла и длины строки.
При ошибке не публикуйте частичный отчёт как успешный.
Закрывайте файлы, результаты SQL-запросов и транзакции.

## 4. PostgreSQL, миграции и перезапуск

В PostgreSQL сохраняются задания, состояния, пути к файлам и готовые отчёты.
Файлы хранятся в Docker volume. Разрешено сохранять весь итоговый отчёт в JSONB.
Самостоятельно спроектируйте таблицы и подготовьте миграции: начальную схему и одно
содержательное изменение, используемое приложением (например, добавление исходного имени файла).
Покажите создание БД с нуля и обновление с сохранением данных.
Миграции выполняются отдельным шагом до запуска приложения; ошибка миграции должна останавливать запуск.

После перезапуска готовые отчёты остаются доступны. При запуске единственной реплики
разрешается переводить оставшиеся `queued` и `running` в `failed` с объяснением
«обработка прервана перезапуском». Пользователь загружает файл повторно.
Продолжение старого задания и автоматический повтор не требуются.
Данные сохраняются при обычном `down`/`up`; удаление volumes означает намеренный сброс.

## 5. Docker, Nginx и пулы

Основной запуск: Nginx → **одна реплика Go** → PgBouncer → PostgreSQL.
Самостоятельно напишите Dockerfile и Docker Compose для приложения, Nginx, PgBouncer
и PostgreSQL. Предусмотрите отдельный шаг миграций, сеть и постоянные тома.
Самостоятельно настройте Nginx: проксирование в Go, ограничение размера загрузки
и запись JSON access-логов в формате задания. Покажите реальный лог после HTTP-запроса.
Запросы к приложению проходят через Nginx.
Самостоятельно настройте PgBouncer: подключение и аутентификацию к PostgreSQL,
режим `transaction`, предел клиентских соединений и размер серверного пула.
Покажите подключение приложения через PgBouncer и состояние пула через `SHOW POOLS`.
Миграции подключаются напрямую к PostgreSQL. Готовые образы Nginx, PostgreSQL и PgBouncer
использовать разрешено; самостоятельно собирать эти программы из исходников не требуется.

В приложении один общий `sql.DB`. Настройте максимальное число открытых и свободных
соединений, используйте таймауты операций с БД через context.
Уметь объяснить разницу между пулом Go и PgBouncer. Собственный пул писать не нужно.
Для подключения подойдёт драйвер PostgreSQL, совместимый с `database/sql`.
При выборе pgx/stdlib проверьте настройки statement cache с transaction pooling;
проще начать с драйвера `github.com/lib/pq` или отключённого кеширования именованных statements.

## 6. dev / test / stage / prod

Самостоятельно подготовьте общий Compose и отдельные настройки окружений.
Достаточно различий в порте, числе worker, размере пула и уровне логирования.
Данные окружений изолированы через разные имена Compose-проектов.
`prod` — локальная демонстрационная конфигурация, а не настоящий публичный сервер.
На stage и prod запускается один собранный образ. Одновременно запускать все окружения не нужно.

## 7. Проверки

Обязательно:

1. Автоматический тест анализатора на контрольном файле и проверка ошибки на испорченной строке.
2. Проверка конкурентного Go-кода с `go test -race ./...`.
3. Демонстрация нескольких заданий при одном и двух worker. Для наглядности разрешена отключаемая задержка.
4. Сохранность готового отчёта после перезапуска.
5. Один эксперимент с `pprof`: получить профиль памяти на большом файле и объяснить,
   какие данные занимают память. Размер файла подбирается под ноутбук.
6. Настроить маленький пул Go, показать его статистику (`DB.Stats`) и объяснить
   возможное ожидание соединения. Отдельный нагрузочный стенд и гарантированное ускорение не требуются.

Диагностику можно включать отдельным локальным портом. Нужны обычные логи с ID задания,
но Prometheus, Grafana и трассировка не требуются.
Дополнительно можно проанализировать завершённую копию access-логов собственного Nginx.

## 8. GitHub и защита

Исходный код обязательно доступен преподавателю на GitHub: публично или через доступ
к приватному репозиторию. Репозиторий содержит код Go, go.mod/go.sum при внешних зависимостях,
тесты, миграции, Docker-конфигурации и README с командами запуска и демонстрации.
Не коммитьте действующие пароли, реальные пользовательские логи и большие сгенерированные файлы.
Укажите коммит сдаваемой версии и покажите её на ноутбуке.

На защите: запустить проект, загрузить контрольный и ошибочный файлы, показать статусы,
отчёт, фоновую обработку, перезапуск и изоляцию test/dev. Объяснить worker, map,
синхронизацию, sql.DB и конфигурацию. Зависимости и образы подготовить заранее.

**Не обязательны:** несколько реплик, отмена и удаление заданий, авторизация,
идемпотентность загрузки, автоматическое восстановление, строгий предел общей очереди,
аварийный сборщик файлов, Kubernetes, CI/CD и фронтенд.
Реплики — добровольное расширение; запуск второй копии потребует изменить получение
заданий и логику старта. Основной проект обещает корректность только с одной репликой.

Допуск определяется работоспособностью перечисленных сценариев и пониманием своего кода,
а не скоростью ноутбука и количеством дополнительных технологий.
